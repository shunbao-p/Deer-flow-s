# 功能方案评审报告：积分到账明细查询与积分过期提醒

## 1. 需求摘要
在会员积分商城基础上，增加积分到账明细查询功能和积分过期提醒机制，以提升积分系统的透明度、公平性和用户活跃度。

## 2. 用户价值
**核心价值**：增强用户对积分资产的掌控感和信任度，通过主动提醒促进积分使用，减少因遗忘导致的积分浪费。

**使用场景**：
- **明细查询**：
  - 用户想了解积分来源，确认消费、活动或任务奖励是否正确到账
  - 用户需要核对积分变动记录，解决积分不符的争议
  - 用户希望分析自己的积分获取模式，优化积分积累策略

- **过期提醒**：
  - 用户在积分即将过期前收到提醒，及时使用避免损失
  - 用户可主动设置提醒偏好（如提前7天、3天、1天）
  - 用户可一次性查看所有即将过期的积分及其可用性

**目标用户群体**：
- 所有积分持有用户，特别是：
  - 积分积累较多但使用不频繁的用户
  - 对账户安全敏感，希望监控所有变动的用户
  - 偶尔使用平台，容易错过积分有效期的用户

**预期效果**：
1. **提升用户满意度**：透明化的明细展示减少用户疑虑和投诉
2. **增加积分使用率**：主动提醒可显著降低积分过期作废的比例
3. **增强平台信任**：完善的记录和提醒机制体现平台对用户资产的重视
4. **促进活跃度**：提醒可能刺激用户为了使用即将过期的积分而返回平台

## 3. 功能拆解

### 3.1 积分到账明细查询模块
**前端功能**：
- 明细列表页：按时间倒序展示所有积分变动记录
- 筛选与搜索：按变动类型（获得/消耗）、时间范围、变动原因筛选
- 详情查看：单条变动记录的完整信息（时间、类型、数量、关联业务、备注）
- 汇总统计：时间段内积分总收入、总支出、净变动

**后端功能**：
- 明细数据模型设计：
  - 用户ID、变动时间、变动类型（增加/减少）、变动数量
  - 业务类型（消费返现、任务奖励、活动赠送、兑换消耗、过期作废等）
  - 关联业务ID（订单号、任务ID、活动ID等）、备注信息
- 查询接口：支持分页、筛选条件、排序
- 数据写入：确保所有积分变动（包括过期）都记录明细

**技术实现要点**：
- 历史数据迁移：如现有积分系统未记录明细，需考虑历史数据的处理方案
- 查询性能：用户可能积累大量明细记录，需优化查询性能（索引设计、分页策略）
- 数据一致性：确保明细记录与积分余额的强一致性

### 3.2 积分过期提醒模块
**提醒规则配置**：
- 积分有效期策略：定义不同类型积分的有效期（如12个月、24个月）
- 过期计算规则：先进先出（FIFO）原则，优先过期最早获得的积分
- 提醒时间点：支持多个提前提醒时间点配置（如30天、15天、7天、3天、1天）

**提醒触发与发送**：
- 定时任务：每日凌晨扫描即将过期的积分记录
- 多渠道提醒：
  - 站内消息/系统通知
  - 邮件提醒（包含即将过期的积分数量、过期时间、可用商品推荐）
  - 短信提醒（针对高价值用户或大额积分）
  - APP推送通知（如已安装移动端）
- 用户偏好设置：允许用户选择接收哪些渠道的提醒，或完全关闭提醒

**前端展示**：
- 过期积分专区：展示即将过期的积分数量、过期时间列表
- 智能推荐：基于即将过期的积分金额，推荐合适的兑换商品
- 一键兑换：从过期积分专区快速跳转到可用商品筛选页面

**技术实现要点**：
- 过期计算准确性：需准确追踪每笔积分的获得时间和对应的有效期
- 定时任务可靠性：确保每日扫描任务稳定执行，无遗漏
- 消息队列：大量提醒发送时使用消息队列解耦，避免阻塞主流程
- 防骚扰机制：同一用户短期内避免重复发送相同提醒

### 3.3 与其他模块的集成
- **与积分账户集成**：明细记录需与积分余额变更保持原子性操作
- **与消息中心集成**：使用平台统一的消息发送服务
- **与商品推荐集成**：过期提醒中可包含个性化商品推荐
- **与风控系统集成**：异常频繁的积分变动明细可作为风控数据源

## 4. 实施风险

**技术风险**：
1. **数据迁移复杂性**：如果现有积分系统未记录明细，历史数据的追溯和初始化复杂
2. **性能与存储压力**：高活跃用户的明细记录可能快速增长，需要合理的归档策略
3. **过期计算的准确性**：先进先出原则的实现复杂性，特别是涉及部分使用、部分过期场景
4. **定时任务稳定性**：每日过期扫描和提醒发送任务必须高可靠，错过可能导致用户损失

**业务风险**：
1. **用户预期管理**：透明化展示明细可能暴露历史规则不一致或数据问题，引发用户质疑
2. **提醒频率把控**：提醒过于频繁可能被视为骚扰，过于稀疏则失去提醒价值
3. **积分过期争议**：即使有提醒，用户仍可能因未及时使用而投诉，需明确免责条款
4. **运营成本增加**：短信、邮件等外部渠道提醒可能产生显著成本

**合规风险**：
1. **数据隐私**：明细记录包含用户行为数据，需符合数据隐私法规
2. **金融属性监管**：如果积分被认定具有金融属性，详细的账务记录可能带来额外合规要求

## 5. MVP范围

**第一阶段MVP（基础功能）**：
1. **基本明细查询**：
   - 列表展示最近90天的积分变动明细
   - 支持按时间倒序排序和分页
   - 仅展示基础信息（时间、类型、数量、简要原因）

2. **基础过期提醒**：
   - 站内消息提醒（提前7天和1天）
   - 过期计算基于简单的"积分获得时间+365天"规则
   - 仅支持系统默认提醒，无用户偏好设置

3. **简化实现**：
   - 历史数据：仅从功能上线后开始记录明细
   - 过期积分：在前端展示"即将过期积分"数量，点击后跳转至商城
   - 提醒内容：固定模板，无个性化商品推荐

**第二阶段迭代**：
1. **明细功能增强**：
   - 完整的筛选搜索功能
   - 更长的历史记录查看（如1年）
   - 明细导出功能（CSV格式）

2. **提醒功能丰富**：
   - 增加邮件提醒渠道
   - 用户偏好设置（提醒开关、提前天数选择）
   - 过期积分专区与商品推荐

3. **高级功能**：
   - 完整的历史数据迁移与展示
   - 多级提醒策略（30/15/7/3/1天）
   - 积分过期前的自动使用建议（如兑换低价虚拟商品）

**优先级建议**：
1. **高优先级**：基础明细查询 + 站内消息提醒（满足最基本透明度和提醒需求）
2. **中优先级**：明细筛选搜索 + 邮件提醒（提升用户体验）
3. **低优先级**：用户偏好设置 + 个性化推荐（精细化运营）

## 6. 给研发的落地建议

**技术架构建议**：

1. **明细数据存储设计**：
   ```sql
   CREATE TABLE point_transaction_details (
     id BIGINT PRIMARY KEY AUTO_INCREMENT,
     user_id BIGINT NOT NULL,
     transaction_time DATETIME NOT NULL,
     transaction_type ENUM('INCREMENT', 'DECREMENT') NOT NULL,
     amount DECIMAL(15,2) NOT NULL,
     balance_after DECIMAL(15,2) NOT NULL,
     business_type VARCHAR(50) NOT NULL, -- 'PURCHASE', 'TASK', 'EXCHANGE', 'EXPIRE'
     business_id VARCHAR(100), -- 关联业务ID
     description VARCHAR(500),
     expire_date DATETIME, -- 该笔积分的过期时间
     INDEX idx_user_time (user_id, transaction_time DESC),
     INDEX idx_user_expire (user_id, expire_date)
   );
   ```

2. **过期计算服务设计**：
   - 采用"积分池"概念，每个用户有一个积分队列，按获得时间排序
   - 消费时从队列头部（最早获得）开始扣除
   - 每日定时任务扫描`expire_date <= CURDATE()`的记录进行过期处理

3. **提醒服务架构**：
   - **扫描服务**：每日01:00运行，查找`expire_date BETWEEN CURDATE() AND CURDATE() + INTERVAL 7 DAY`的记录
   - **消息生成服务**：根据扫描结果生成提醒消息
   - **消息发送服务**：对接各渠道（站内信、邮件、短信）统一发送
   - 使用消息队列解耦各环节，提高系统韧性

**API接口设计**：
- `GET /api/points/transactions` - 获取积分明细列表
- `GET /api/points/expiring` - 获取即将过期积分列表
- `POST /api/points/reminder/preferences` - 更新提醒偏好设置
- `POST /api/internal/points/expire-scan` - 内部过期扫描触发接口

**关键实现细节**：

1. **事务一致性**：
   ```python
   # 积分变动与明细记录必须在同一事务中
   @transaction.atomic
   def add_points(user_id, amount, business_type, business_id):
       # 更新用户积分余额
       account = PointAccount.objects.select_for_update().get(user_id=user_id)
       account.balance += amount
       account.save()
       
       # 记录明细
       PointTransaction.objects.create(
           user_id=user_id,
           transaction_time=now(),
           transaction_type='INCREMENT',
           amount=amount,
           balance_after=account.balance,
           business_type=business_type,
           business_id=business_id,
           expire_date=calculate_expire_date(now())
       )
   ```

2. **过期处理幂等性**：
   - 过期操作必须幂等，防止重复过期扣减
   - 使用状态标志或检查`expire_date`是否已被处理

3. **性能优化**：
   - 明细查询使用复合索引`(user_id, transaction_time)`
   - 考虑定期归档历史明细到历史表
   - 过期扫描使用分批处理，避免大事务锁表

**测试重点**：
1. **明细准确性测试**：模拟各种积分变动场景，验证明细记录与余额的一致性
2. **过期计算测试**：测试FIFO原则在各种消费模式下的准确性
3. **并发测试**：高并发下的积分变动与明细记录的数据一致性
4. **提醒触发测试**：验证定时任务在各种边缘情况下的可靠性

**监控与告警**：
- 监控每日过期积分数量与用户投诉比例
- 设置提醒发送失败告警
- 监控明细查询接口的响应时间与错误率

**数据迁移策略**（如有历史数据）：
1. **方案A（推荐）**：仅从新功能上线后开始记录明细，历史数据提供汇总统计
2. **方案B（高成本）**：通过业务日志反向生成历史明细，适用于对完整性要求极高的场景
3. **渐进式展示**：初期仅展示近期明细，随着时间推移逐步补充历史数据查询能力

---

### 总结与建议
这两个新增功能是积分商城系统的重要组成部分，能显著提升用户体验和积分使用效率。建议采用分阶段实施策略：

1. **立即实施**：基础明细查询（90天内记录）+ 站内消息提醒（提前7天）
2. **短期迭代**：完善明细筛选功能 + 增加邮件提醒渠道
3. **长期优化**：完整的用户偏好设置 + 个性化推荐 + 历史数据支持

技术实现上需特别关注数据一致性（明细与余额）、过期计算的准确性、以及提醒系统的可靠性。建议先采用简化的MVP方案快速上线验证价值，再根据用户反馈和数据分析逐步完善。
